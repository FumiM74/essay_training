# サービス実装方針

最終更新: 2026-08-26

このファイルを、サービス実装に関する設計判断の唯一の正本とする。`handoff.md`と`../curriculum-design/小論文添削サービス_カリキュラム設計.xlsx`は、経緯と教育内容の参照資料として保持する。

## 採用構成

- PWA: SvelteKit + TypeScript（Vite内蔵）
- 認証・DB・RLS・リアルタイム・サーバー処理: Supabase Auth、PostgreSQL、RLS、Realtime、Edge Functions
- 配信・ボット対策: Cloudflare Pages + Turnstile
- 課金: Stripe。決済状態はWebhookから`entitlements`へ反映し、アプリは利用権だけを参照する。
- メール: Resend（Supabase Authの本番SMTP、決済・障害通知）
- AI添削: Claude API。実装はモデルプロバイダーを差し替え可能にする。

Cloudflare Workersは初期構成に含めない。添削キュー、負荷平準化、追加のAPIゲートウェイが必要になった時だけ導入する。

## シンプルなフォルダ構成

```text
web/                  SvelteKitの学習者向けPWAと開発用変換処理
  scripts/            カリキュラムExcel→JSON変換
  src/lib/features/learning/  段階・進捗・合格・問題選択の学習ルール
  src/lib/features/   学習、認証、課金の画面機能
  src/lib/services/   Supabase接続
  src/lib/types/      UserSession、AccessState、API・添削結果の型
  static/             PWAアイコン・manifest
supabase/             DB・RLS・Edge Functions
  migrations/         PostgreSQLスキーマ、RLS、DB関数
  functions/          feedback、create-checkout、stripe-webhook、admin
docs/                 設計・運用記録
```

SvelteKitを使うのは`web/`だけとする。`node_modules/`、`.svelte-kit/`、`build/`などの自動生成物も同じディレクトリ内に閉じ、Git管理しない。

## 境界契約

- `UserSession`: `userId`と`role`。学習ルールは認証実装に依存しない。
- `AccessState`: `canSubmit`、プラン、有効期限、残提出数。学習画面はStripeの決済詳細に依存しない。
- `FeedbackResult`: JSON Schemaで検証済みの添削結果だけを表示・保存する。

ブラウザにClaude APIキー、Stripe秘密鍵、Supabase service-roleキーを置かない。正式提出・添削・決済WebhookはEdge Functionで処理する。

## 実装順

1. `web/`のSvelteKit、共通型、開発・テスト基盤を作る。
2. DBスキーマ、RLS、権限テストを`supabase/migrations/`へ追加する。
3. カリキュラムExcelからJSONを生成・検証する。
4. AIモックで、課題、下書き自動保存、提出、結果、履歴、進捗を作る。
5. Claude添削の`feedback` Edge Functionを実装する。
6. 管理者機能を加える。
7. Turnstile、レート制限、メール、削除・バックアップ運用を加える。
8. Stripeと利用権を実装する。
9. 少人数テスト後に一般公開する。

## ローカルMVP

Supabase接続前に、次の学習フローをローカルで検証する。

- カリキュラムExcelから段階0〜13を読み込み、問題生成用のテーマテンプレートJSONを生成する。段階・ルーブリックはExcel、練習テーマ群は`web/scripts/practice-bank.ts`を正本とする。テンプレート数は学習者に提示する問題数の上限ではない。
- 課題一覧、課題詳細、下書き自動保存、モック添削、提出履歴、学習進捗を一続きで操作できるようにする。
- 下書きと提出履歴は`localStorage`へ保存し、後でサービス層をSupabaseへ差し替える。
- 初期の進級条件は同じ段階で3問連続合格とする。不合格では連続回数を0へ戻し、条件達成時だけ次段階へ進む。段階13で条件を満たすと全課程修了とする。
- 学習者は必要な連続合格回数を1〜10回で変更できる。変更しても現在の連続合格数は保持し、次回以降の判定に新しい条件を使う。
- 各段階の問題数は固定しない。カリキュラムの到達目標と出題設計は固定するが、学習者に見せる問題文を固定テンプレートの直積だけで作らない。学習履歴から今回の訓練目標を選ぶ「適応制御」、自然な問題文を作る「生成」、教育条件・安全性・重複を確認する「検証」を分離する。
- 問題履歴には、意味不明な連続値ベクトルではなく、段階別に意味が定義された`feature_signature`を保存する。全段階で`topic_domain`、`topic_key`、`prompt_family`、`skill_targets`、`fingerprint`を持ち、必要になった段階から`language_pattern`、`perspective`、`reasoning`、`evidence_mode`、`source_structure`、`issue_conflict`、`counterposition`を追加する。該当しない特徴へ架空の既定値を入れない。
- 問題本文全体や全履歴をClaudeへ再送して重複判定しない。サーバーが短い特徴署名、直近の問題指紋、学習者の苦手技能を選び、Claudeには今回必要な条件だけを渡す。概念の重複は特徴署名、表現の重複は問題文の正規化ハッシュとローカル計算の文字・単語n-gram類似度で判定する。外部Embedding APIは初期実装では使わない。
- 表示した問題も`problem_history`へ記録し、未提出の問題は再表示する。提出後は段階内の問題履歴と全段階のテーマ利用回数を使って次問を選ぶ。到達済み段階へ戻っても履歴と苦手傾向を失わない。
- 1つの発行済み問題は1回だけ提出・進級判定へ計上する。通信再送では`request_id`、別の送信IDや複数タブからの競合では`task_key`を使って二重計上を防ぐ。提出後の再練習には、履歴を踏まえて選んだ次の問題を使う。
- `current_stage_id`（現在取り組む段階）と`highest_unlocked_stage_id`（最高到達段階）を分離する。学習者は到達済み段階へ自由に戻れるが、未解放段階は選択・提出できない。段階変更時は連続合格数を0へ戻す。
- ローカル保存形式はversion 4とし、旧version 1〜3から問題履歴、段階別特徴署名、最高到達段階を再構築する。旧ベクトルから推定できない技能別結果は捏造せず、移行後の提出から蓄積する。
- 日次活動はモック添削への提出を1活動として数える。自動保存は過剰計上を避けるため活動に含めない。
- GitHub風グリッドは本人のローカル提出履歴だけを年単位で表示する。

## 適応出題・自然文生成の最終設計

### 基本原則

- テンプレートは学習者へそのまま表示する定型文ではなく、段階ごとの教育目標、必須要素、禁止事項、採点観点を定める「問題設計図」として使う。
- 出題内容の個別最適化と、問題文の自然な表現を別処理にする。個人差は適応制御で扱い、自然さは問題生成器で扱う。
- 進級条件は必要連続合格回数のまま維持する。適応出題は合格条件を緩めず、何を重点的に練習するかだけを変える。
- 苦手問題だけが続いて学習者が固定化されないよう、初期比率は「苦手技能50%・段階の中核技能30%・未経験の題材や組合せ20%」とする。履歴が少ない間は中核技能と多様性を優先する。

### 13段階に応じて保持する特徴

| 対象段階 | 主な訓練 | 追加して使う特徴 |
|---|---|---|
| 1〜2 | 文の成立・明確さ | `language_pattern` |
| 3 | 主張・立場 | `perspective` |
| 4〜5 | 理由・因果の深化 | `reasoning` |
| 6 | 具体例・根拠 | `evidence_mode` |
| 7 | 段落構成 | `structure_pattern` |
| 8〜9 | 読解・要約 | `source_structure`、`summary_operation` |
| 10 | 資料に基づく意見 | `issue_conflict`、`source_use` |
| 11 | 反対意見への応答 | `counterposition`、`response_strategy` |
| 12〜13 | 複数要素を統合した小論文 | 上記のうち課題に必要な複数特徴、`synthesis_pattern` |

全段階で`topic_domain`、`topic_key`、`prompt_family`、`skill_targets`を保存する。これにより段階1から題材経験を蓄積し、後半では同一分野への偏りを避けられる。時間軸、想定読者、利害関係者は全段階の共通軸にはしない。課題の教育目標として必要な場合だけ`perspective`や`issue_conflict`の一部として持たせる。

### 学習者の苦手傾向

- 各提出の添削結果を、合否だけでなく`skill_results`として保存する。1件には`skill_key`、`outcome`（達成・一部達成・未達）、`severity`、短い根拠を持たせる。
- 学習者×段階×技能の集計を`learner_skill_stats`へ保存する。試行数、達成数、未達数、直近結果、習熟度、最終練習日時を持ち、次問選択に使う。
- 習熟度は直近の結果をやや強く反映しつつ、1回の失敗だけで極端に変化しない更新式にする。合否と技能別評価の両方をテスト可能な決定的関数として実装する。
- 誤りの原文を問題生成のたびにClaudeへ渡さない。必要なら「主張が曖昧」「因果の飛躍」「具体例不足」などの短い技能コードと強度だけを渡す。詳しい答案本文は添削時だけ扱う。

### 問題を作る処理

1. 現在段階、未達技能、直近の練習量、全段階の題材経験から、今回の`ProblemSpecification`を決める。
2. 同じ特徴署名・題材・表現型が直近履歴と重ならない候補を選ぶ。
3. 承認済み問題バンクに適切な問題があれば再利用する。ただし同じ学習者へ同一問題は再発行しない。
4. 適切な問題がなければ、Claudeへ短い`ProblemSpecification`と段階別問題設計図だけを渡し、構造化JSONで1問生成する。生成結果は検証後に共有問題バンクへ保存し、他の学習者にも再利用してコストを分散する。
5. 段階、必須要素、文量、答えの混入、禁止表現、特徴署名、表面上の類似度をサーバーで検証する。不合格なら1回だけ再生成し、それでも不合格なら承認済み問題へフォールバックする。
6. 発行と同時に、使用した設計版、生成元（承認済み・AI生成）、モデル、プロンプト版、特徴署名、本文ハッシュを履歴へ保存する。

段階1〜7も自然文生成の対象にできるが、毎回のリアルタイム生成を必須にしない。短い問題を事前生成・検証して問題バンクへ蓄積し、学習者の苦手技能に合う在庫がない場合だけ追加生成する。段階8〜9の読解素材は著作権と事実性を管理できる承認済み・合成素材を優先し、段階10〜13では多様な論点と対立軸を使う。

### トークン効率と将来のEmbedding

- Claudeへ渡すのは、今回の段階設計、狙う技能コード、題材コード、必要な論証・資料条件、避ける直近指紋だけとする。過去答案、全問題文、全特徴ベクトルは渡さない。
- 初期の題材は管理済み分類なので、カテゴリコードと利用回数で十分に多様性を管理できる。自由入力の新規テーマが増え、既存分類へ安定して割り当てられなくなった時だけ、短い`topic_summary`を1本Embedding化する。
- Embeddingを追加しても、段階別技能、論証方法、資料構造などの明示的特徴を置き換えない。説明可能な特徴署名を主、Embeddingを未知テーマの補助とする。

### AI利用量とコスト制御

- 問題生成は承認済み問題バンクを最優先し、狙う技能に合う未出題問題がない場合だけAIを呼ぶ。AI生成問題は検証後に共有問題バンクへ保存し、同じ生成費用を複数学習者で再利用する。
- 添削は答案ごとに必要なため、問題生成より多くの予算を割り当てる。過去答案や全履歴は添削入力へ含めず、今回の問題、答案、対象技能、必要なルーブリックだけを送る。
- 現在の数値（問題生成1回あたり入力1,800・出力700トークン、学習者1日3回、添削1回あたり入力6,000・出力1,800トークン、学習者1日20回）は、開発中の暴走を防ぐためだけの**暫定ガード値**である。問題と添削の品質へ直結するため、本番仕様・料金プランとして確定してはならない。
- 最終リリーステストでは、実測した入力・出力・キャッシュ・失敗率・応答品質・1学習者あたり費用を提示し、サービス所有者へ本番上限を必ず確認する。明示的な承認を得て`ai_budget_policies.review_status`を`approved`へ変更するまでは、AI利用量設定に関する最終テストを完了扱いにしない。
- 実請求の集計には推定値ではなく、プロバイダー応答の入力・出力・キャッシュ作成・キャッシュ読込トークンを使う。`ai_usage_events`へ処理種別、モデル、状態、各トークン数、料金表版、任意の概算費用を保存する。
- 料金単価とモデル名をアプリへ固定しない。`ai_budget_policies`の上限とサーバー側環境設定で変更できるようにし、ブラウザへAPIキーや内部原価を渡さない。
- 予算超過、生成無効、検証失敗時も学習を止めず、承認済み問題またはローカル問題へフォールバックする。添削の予算超過時は、正式添削を行っていないことを明示して再試行可能な状態を返し、モック結果を正式成績として保存しない。

## 認証・DB接続済みのローカル開発版

- 認証はSupabase Authのメール＋パスワードを使用する。確認メールと再設定メールの戻り先は、Supabase AuthのURL allow-listで限定する。
- `web/.env.local`にProject URLとPublishable keyを置く。前者は接続先、後者はブラウザ用の公開キーであり、Git管理しない。
- 未設定時だけローカル体験版として動かす。Supabase設定済みの未ログイン状態ではローカルデータを表示・保存せず、ログインを求める。既存のローカルデータを無断でクラウドへ移さない。
- 学習者の下書き、提出、添削結果は正式テーブル`drafts`、`submissions`、`feedback_results`へ保存する。試作用の重複テーブルは作らない。
- `learning_progress`に現在段階、最高到達段階、連続合格数、学習者が選んだ必要連続合格回数、全課程修了日時を保存する。学習者が直接更新できるのは必要回数だけとし、段階移動は上限を検証するDB関数を経由する。
- `problem_history`に発行済み問題、段階別`feature_signature`、問題指紋、本文ハッシュ、設計・生成版、発行・提出日時を保存する。ブラウザには本人分だけを返し、発行は現在段階を検証するDB関数を経由する。
- 下書きは500msのデバウンスと直列保存で競合を防ぐ。提出前には保留中の下書き保存を完了させる。
- モック提出は`request_id`と問題の`task_key`で冪等化し、提出・添削結果保存・下書き削除・連続合格判定・進級を`submit_mock` DB関数の1トランザクションで行う。同じ問題を異なる送信IDで送っても1回しか計上しない。Claude接続時は同じ境界をEdge Functionへ置き換える。
- 問題発行は学習進捗行をロックして直列化し、同じ段階ですでに未提出問題があれば新規発行しない。ローカル保存でも同じ制約を適用する。
- Data APIのテーブル自動公開は無効とし、必要な`authenticated`権限だけをマイグレーションで明示的に付与する。
- `profiles`は認証済み学習者に対して`display_name`列だけを更新許可する。`role`列の更新権限はPostgreSQLの列権限で明示的に剥奪し、RLSだけに依存しない。
- パスワード再設定は`PASSWORD_RECOVERY`イベントを検出し、確認用入力後に`updateUser`で完了させる。
- この段階で保存する添削結果は決定的なモック結果だけであり、正式な成績として扱わない。Claude連携後は`submit_mock`の実行権限を廃止し、Edge Functionだけが正式な提出と添削結果を作成する。

ローカルMVPはClaude、Stripeの代替ではない。認証、DB保存、RLSの実接続確認後にClaude添削と課金を接続する。

## 実装前のデータ確認

カリキュラムExcelの段階13とAI指示設計には完全一致の重複行が3件ずつある。ローカルMVPの変換処理は完全一致行だけを決定的に除外し、同じ識別子に異なる内容がある場合はエラーにする。原本側の重複削除は次回の教育内容編集時に行う。
