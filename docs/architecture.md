# サービス実装方針

最終更新: 2026-09-06

このファイルを、サービス実装に関する設計判断の唯一の正本とする。`handoff.md`と`../curriculum-design/小論文添削サービス_カリキュラム設計.xlsx`は、経緯と教育内容の参照資料として保持する。

## 採用構成

- PWA: SvelteKit + TypeScript（Vite内蔵）
- 認証・DB・RLS・リアルタイム・サーバー処理: Supabase Auth、PostgreSQL、RLS、Realtime、Edge Functions
- 配信・ボット対策: Cloudflare Workers（SvelteKit公式アダプター）+ Turnstile
- 課金: Stripe。決済状態はWebhookから`entitlements`へ反映し、アプリは利用権だけを参照する。
- メール: Resend（Supabase Authの本番SMTP、決済・障害通知）
- AI添削: Claude API。実装はモデルプロバイダーを差し替え可能にする。

Cloudflare WorkersはSvelteKit画面の配信に使う。認証、学習データ、正式添削、決済WebhookはSupabase側へ集約し、同じ秘密情報や業務処理をCloudflare側へ二重実装しない。添削キューや追加APIゲートウェイは、実測して必要になった場合だけ導入する。

## シンプルなフォルダ構成

```text
web/                  SvelteKitの学習者向けPWAと開発用変換処理
  scripts/            カリキュラムExcel→JSON変換
  src/lib/features/learning/  段階・進捗・合格・問題選択の学習ルール
  src/lib/features/   学習、認証、課金の画面機能
  src/lib/services/   Supabase接続
  src/lib/types/      UserSession、AccessState、API・添削結果の型
  static/             PWAアイコン・manifest
supabase/             DB・RLS・Edge Functions
  migrations/         PostgreSQLスキーマ、RLS、DB関数
  functions/          feedback、create-checkout、stripe-webhook、admin
docs/                 設計・運用記録
```

SvelteKitを使うのは`web/`だけとする。`node_modules/`、`.svelte-kit/`、`build/`などの自動生成物も同じディレクトリ内に閉じ、Git管理しない。

## 境界契約

- `UserSession`: `userId`と`role`。学習ルールは認証実装に依存しない。
- `AccessState`: `canSubmit`、プラン、有効期限、残提出数。学習画面はStripeの決済詳細に依存しない。
- `FeedbackResult`: JSON Schemaで検証済みの添削結果だけを表示・保存する。

ブラウザにClaude APIキー、Stripe秘密鍵、Supabase service-roleキーを置かない。正式提出・添削・決済WebhookはEdge Functionで処理する。

## 実装順

1. `web/`のSvelteKit、共通型、開発・テスト基盤を作る。
2. DBスキーマ、RLS、権限テストを`supabase/migrations/`へ追加する。
3. カリキュラムExcelからJSONを生成・検証する。
4. AIモックで、課題、下書き自動保存、提出、結果、履歴、進捗を作る。
5. Claude添削の`feedback` Edge Functionを実装する。
6. 管理者機能を加える。
7. Turnstile、レート制限、メール、削除・バックアップ運用を加える。
8. Stripeと利用権を実装する。
9. 少人数テスト後に一般公開する。

## ローカルMVP

Supabase接続前に、次の学習フローをローカルで検証する。

- 旧カリキュラムExcelの日本語成立チェックを参照しつつ、`web/scripts/convert-curriculum.ts`の14段階設計と`web/scripts/practice-bank.ts`の問題設計から段階0〜14のJSONを生成する。設計判断の正本は本書とし、旧Excelの段階表は経緯資料として扱う。テンプレート数は学習者に提示する問題数の上限ではない。
- 課題一覧、課題詳細、下書き自動保存、モック添削、提出履歴、学習進捗を一続きで操作できるようにする。
- 下書きと提出履歴は`localStorage`へ保存し、後でサービス層をSupabaseへ差し替える。
- 各段階は「通常トレーニング→進級テスト→次段階」のループとする。
- 通常トレーニングは初期値10問（段階1では10セット）の合格で進級テストへ移る。全段階の要修正答案は同じ問題で修正・再提出でき、不合格でも現在の合格数は減らさない。
- 段階1は、主語・述語、助詞、助動詞・文末、語順・修飾、文の完成・修正から1問ずつ選ぶ5問1セットとする。5問すべての正解で1セット合格とし、正誤にかかわらず全問へ解説を返す。通常トレーニングで不正解があれば「解答を修正する」から同じセットへ戻る。正解済みの解答は保持して編集不可とし、不正解の問題に「ここを修正」のラベルと強調枠を表示する。再読み込み時も提出結果と下書きから解答を復元する。解説を読んで修正することを学習とし、一発での理解確認は進級テストで行う。
- 段階2は「情報の関係を示す」「曖昧さを直す」「必要な情報を選ぶ」の3問1セットとし、単に「から」「ため」を補うだけの反復にはしない。段階3は「文の順序を決める」「不足する論理を補う」「重複・脱線を除いて流れを直す」の3問1セットとし、2〜4文を扱う。段階2・3とも3問すべての正解で1セット合格とし、通常トレーニングでは正解済みの解答を保持して不正解の問題だけを修正・再提出できる。進級テストでは一度だけ提出し、未合格なら次の問題セットへ進む。
- 添削モデルは、短い文法判断が中心の段階1と短い意見・理由を扱う段階4をHaiku、複数の自由記述を同時に評価する段階2・3と段階5以降をSonnetとする。段階3は再設計により文順・論理の不足・重複修正を扱うため、旧設定のHaikuからSonnetへ変更する。
- 進級テストは各問題に1回だけ解答する。不合格でも要修正・再提出にはせず、合格数を保持したまま新しい問題へ進む。合格は連続である必要はなく、1回の進級テスト中に初期値3問へ合格した時点で次段階へ進む。段階14で達成すると全課程修了とする。
- 学習者は通常トレーニングと進級テストの必要合格数をそれぞれ1〜10問で変更できる。変更しても現在の合格数は保持し、次回以降の判定に新しい条件を使う。
- 各段階の問題数は固定しない。カリキュラムの到達目標と出題設計は固定するが、学習者に見せる問題文を固定テンプレートの直積だけで作らない。学習履歴から今回の訓練目標を選ぶ「適応制御」、自然な問題文を作る「生成」、教育条件・安全性・重複を確認する「検証」を分離する。
- 問題履歴には、意味不明な連続値ベクトルではなく、段階別に意味が定義された`feature_signature`を保存する。全段階で`topic_domain`、`topic_key`、`prompt_family`、`skill_targets`、`fingerprint`を持ち、必要になった段階から`language_pattern`、`perspective`、`reasoning`、`evidence_mode`、`source_structure`、`issue_conflict`、`counterposition`を追加する。該当しない特徴へ架空の既定値を入れない。
- 問題本文全体や全履歴をClaudeへ再送して重複判定しない。サーバーが短い特徴署名、直近の問題指紋、学習者の苦手技能を選び、Claudeには今回必要な条件だけを渡す。概念の重複は特徴署名、表現の重複は問題文の正規化ハッシュとローカル計算の文字・単語n-gram類似度で判定する。外部Embedding APIは初期実装では使わない。
- 表示した問題も`problem_history`へ記録し、未提出の問題は再表示する。提出後は段階内の問題履歴と全段階のテーマ利用回数を使って次問を選ぶ。到達済み段階へ戻っても履歴と苦手傾向を失わない。
- 通常トレーニングの要修正答案は、段階1も含め同じ発行済み問題へ何度でも再提出でき、各提出と添削結果を履歴へ残す。問題の合格は最初の合格提出だけを進級判定へ計上する。通信再送は`request_id`で冪等化し、合格済み`task_key`への別送信IDも二重計上しない。変更前に完了扱いとなった過去の不合格セットは自動で再開しない。
- 提出履歴では各記録に提出時点の「トレーニング」または「進級テスト」を表示する。通常トレーニングの未合格は「要修正」、進級テストの未合格は再提出しないため「不合格」と表示する。段階1の5問セットは採点結果を要約せず、問題1〜5それぞれの問題文、学習者の解答、正誤、説明を対応づけてすべて表示する。問題バンクを将来変更しても過去の表示が変わらないよう、段階1では提出時の問題文と解答も`feedback_results.result`内へスナップショット保存し、既存履歴だけ問題IDから復元する。
- 課題トップの段階状態は、現在の段階を薄いオレンジ色の「学習中」、到達済み段階を「完了」、未到達段階を「未完了」と表示する。段階カードには問題数の上限を示す定型文を表示しない。履歴から課題トップへ戻るリンクは「課題トップ画面へ」とする。
- `current_stage_id`（現在取り組む段階）と`highest_unlocked_stage_id`（最高到達段階）を分離する。学習者は到達済み段階へ自由に戻れるが、未解放段階は選択・提出できない。別段階に未提出課題があっても段階変更を妨げず、その課題は削除せずに保持して、該当段階へ戻ったときに再開する。段階変更時は通常トレーニングから開始し、フェーズ内合格数を0へ戻す。
- ローカル保存形式はversion 5とし、旧version 1〜4から問題履歴、段階別特徴署名、最高到達段階を再構築する。旧連続合格数は通常トレーニングの合格数として保持する。旧ベクトルから推定できない技能別結果は捏造せず、移行後の提出から蓄積する。
- 日次活動はモック添削への提出を1活動として数える。自動保存は過剰計上を避けるため活動に含めない。
- GitHub風グリッドは本人のローカル提出履歴だけを年単位で表示する。

## 適応出題・自然文生成の最終設計

### 基本原則

- テンプレートは学習者へそのまま表示する定型文ではなく、段階ごとの教育目標、必須要素、禁止事項、採点観点を定める「問題設計図」として使う。
- 出題内容の個別最適化と、問題文の自然な表現を別処理にする。個人差は適応制御で扱い、自然さは問題生成器で扱う。
- 進級条件は通常トレーニングと進級テストの状態機械で一貫して判定する。適応出題は合格条件を緩めず、何を重点的に練習するかだけを変える。進級テストでは中核技能を優先し、不合格時も履歴を使って異なる新問題を出す。
- 苦手問題だけが続いて学習者が固定化されないよう、初期比率は「苦手技能50%・段階の中核技能30%・未経験の題材や組合せ20%」とする。履歴が少ない間は中核技能と多様性を優先する。

### 14段階に応じて保持する特徴

| 対象段階 | 主な訓練 | 追加して使う特徴 |
|---|---|---|
| 1〜2 | 文の基礎・明確さ | `language_pattern` |
| 3 | 文と文の関係 | `language_pattern` |
| 4〜5 | 意見・理由・因果の深化 | `perspective`、`reasoning` |
| 6 | 具体例・根拠 | `evidence_mode` |
| 7 | 段落分析・修正 | `source_structure`、`structure_pattern` |
| 8 | 段落構成 | `structure_pattern` |
| 9 | 要約 | `source_structure`、`summary_operation` |
| 10 | 資料に基づく意見 | `issue_conflict`、`source_use` |
| 11 | 反対意見への応答 | `counterposition`、`response_strategy` |
| 12 | 構成メモ | `reasoning`、`synthesis_pattern` |
| 13〜14 | 複数要素を統合した小論文 | 上記のうち課題に必要な複数特徴、`synthesis_pattern` |

全段階で`topic_domain`、`topic_key`、`prompt_family`、`skill_targets`を保存する。これにより段階1から題材経験を蓄積し、後半では同一分野への偏りを避けられる。時間軸、想定読者、利害関係者は全段階の共通軸にはしない。課題の教育目標として必要な場合だけ`perspective`や`issue_conflict`の一部として持たせる。

段階2では、二つの内容を「内容①」「内容②」と句点付きで分けて提示し、順序や言葉の形を調整して一文にまとめさせる。元文を句点なしで並べず、素材の区切りと求める解答形式を明示する。段階3は二文を一文へまとめる課題ではない。元の二文を保ち、二文目の冒頭に「なぜなら」「一方」「また」など前文との関係を示す言葉を加えたうえで、二文全体を解答させる。課題文・ヒント・解答例・AI生成指示はこの形式に統一する。

### 学習者の苦手傾向

- 各提出の添削結果を、合否だけでなく`skill_results`として保存する。1件には`skill_key`、`outcome`（達成・一部達成・未達）、`severity`、短い根拠を持たせる。
- 学習者×段階×技能の集計を`learner_skill_stats`へ保存する。試行数、達成数、未達数、直近結果、習熟度、最終練習日時を持ち、次問選択に使う。
- 習熟度は直近の結果をやや強く反映しつつ、1回の失敗だけで極端に変化しない更新式にする。合否と技能別評価の両方をテスト可能な決定的関数として実装する。
- 誤りの原文を問題生成のたびにClaudeへ渡さない。必要なら「主張が曖昧」「因果の飛躍」「具体例不足」などの短い技能コードと強度だけを渡す。詳しい答案本文は添削時だけ扱う。

### 問題を作る処理

1. 現在段階、未達技能、直近の練習量、全段階の題材経験から、今回の`ProblemSpecification`を決める。
2. 同じ特徴署名・題材・表現型が直近履歴と重ならない候補を選ぶ。
3. 承認済み問題バンクに適切な問題があれば再利用する。ただし同じ学習者へ同一問題は再発行しない。
4. 適切な問題がなければ、Claudeへ短い`ProblemSpecification`と段階別問題設計図だけを渡し、構造化JSONで1問生成する。生成結果は検証後に共有問題バンクへ保存し、他の学習者にも再利用してコストを分散する。
5. 段階、必須要素、文量、答えの混入、禁止表現、特徴署名、表面上の類似度をサーバーで検証する。不合格なら1回だけ再生成し、それでも不合格なら承認済み問題へフォールバックする。
6. 発行と同時に、使用した設計版、生成元（承認済み・AI生成）、モデル、プロンプト版、特徴署名、本文ハッシュを履歴へ保存する。

段階1〜8も自然文生成の対象にできるが、毎回のリアルタイム生成を必須にしない。短い問題を事前生成・検証して問題バンクへ蓄積し、学習者の苦手技能に合う在庫がない場合だけ追加生成する。段階7・9の読解素材は著作権と事実性を管理できる承認済み・合成素材を優先し、段階10〜14では多様な論点と対立軸を使う。

### 段階別の問題表示と添削

- 課題本文には「何を書くか」だけを簡潔に示す。主語・述語、修飾関係、論証方法などの評価上の注意は、課題本文へ継ぎ足さず「ヒント」と「合格の目安」に分離する。
- 通常トレーニングの段階2〜6では、全学習者共通の固定解答例を「ヒント」の直下に表示する。各例には、例文中のどの語句・構成がヒントを満たすかを説明する「ポイント」を添える。段階1は問題ごとの正解と解説を採点後に表示するため、事前の固定解答例を出さない。段階7以降は固定解答例を表示しない。進級テストにも解答例を表示しない。
- 全14段階のヒントと添削コメントは、「確認する」「働きを確かめる」「関係を明確にする」だけで終えない。学習者が次に行う操作を、「どの言葉を、どこへ移す・何へ置き換える・何の後に加える」のように具体的に書く。主語・述語、助詞などの用語を使う場合は、「誰が・何が」「どうする・どのようだ」「が・を・に・で」のような例を同じ説明に添える。
- ヒントは原則として二文程度に収める。最初の文で着目する文章要素や書く順序を示し、次の文で読み手にどのように伝わればよいかを示す。ローカル派生問題でも説明を機械的に追加せず、段階ごとに整えた同じヒントを使う。
- 文字数だけで合否を決めず、課題文にない最低文字数をClaudeやローカルモックが追加しない。オンライン環境では段階1もClaudeで5問を一括採点し、記述式の表記揺れや意味の等しい自然な言い換えを許容する。5問すべての正解だけを1セット合格とし、各問の問題・解答・正誤・正解例・解説を保存する。ローカル試作モードだけは、外部費用なしで画面遷移を確認するため決定的なモック採点を残す。
- Claudeへは現在段階の評価焦点、まだ要求しない後続技能、今回の対象技能、短いルーブリック、課題、答案だけを渡す。後の段階で学ぶ技能がないことを理由に不合格にしない。
- 要修正時の助言は最優先の1点に絞り、次の再提出で直せる具体的な表現にする。合格時は答案中の表現を根拠に、良かった点と任意の改善案を2〜3件返す。
- 提出直後の上部表示は、通常トレーニングでは「合格」または「要修正」、進級テストでは「合格」または「不合格」と、現在合格数・必要合格数を示す。進級テストの不合格時は合格数を保持して次問題へ進むことを明示する。
- 合格後は解答用の「今回の課題」「あなたの解答」カードを非表示にし、添削結果カード内へ今回の課題、提出した解答、詳しいコメント、合格根拠、次問ボタンをまとめる。通常トレーニングと進級テストで同じ情報構造を使う。
- 課題画面の遷移は、全段階の通常トレーニングで要修正なら同じ発行済み問題の修正画面へ戻し、入力欄へフォーカスする。段階1は最初の不正解問題へスクロールする。進級テストの合否、通常トレーニングの合格は次の新しい問題へ進む。全課程修了時は新しい問題を出さず、学習結果画面へ進む。
- 解答可能かどうかは、画面で再計算した推奨問題だけでなく、DB上で未提出の発行済み問題とも照合する。これにより、要修正後の再読込や状態更新のタイミングで同じ問題の入力欄が誤って無効になることを防ぐ。現在段階ではない古いURLや完了済み問題は引き続き入力不可とする。
- 問題発行は同一ユーザー・同一段階で冪等にする。ブラウザ内では同時要求を共有し、複数タブや通信再送が競合した場合もDBの一意制約に先着した未完了問題を採用して、後続要求をエラーにしない。
- 段階1の問題識別値は、共通の課題見出しではなく、5問それぞれの種別・指示・問題文・選択肢を正規化して作る。異なる5問セットを重複と誤判定せず、同じ内容のセットは再出題しない。

#### 保存と結果表示の安全性

- 提出後は合否と残り合格数の枠を画面上端へスクロールする。枠内に合格（緑）／要修正・不合格（オレンジ）の大きなラベルを置く。詳細欄の見出しは全段階「結果」に統一し、右上の合否ラベルは重複表示しない。修正画面の正解済みラベルは「正解」とし、解答保持・編集禁止は維持する。提出履歴の不正解小問題にも修正画面と同じオレンジ色の枠・背景・ラベルを使う。

- 未出題候補が尽きた場合、重複検査を省略した問題へフォールバックしない。在庫切れを明示し、問題追加を待つ。現在のモック問題群は有限であり、継続的な補充はClaude問題生成の接続時に実装する。
- 問題発行の競合を成功として扱うのは、同じ段階に未完了の発行済み問題が存在する場合だけとする。使用済み問題との衝突だけで未完了問題が存在しない場合はDBが拒否し、発行を確認できない問題の入力は許可しない。
- 提出中は入力を停止し、課題・答案・添削・提出前の進捗をスナップショットとして保持する。結果画面には提出時の内容を表示する。
- 提出保存と保存後の進捗取得を区別する。保存成功後の取得失敗では結果を保持して「進捗を再読み込む」を表示し、再提出せず取得だけを再試行する。
- 結果画面の合格数は提出した区分で表示する。トレーニング最終合格は10/10、進級テスト最終合格は3/3などとし、次区分の0件表示に置き換えない。
- 過去の全課程修了日は、戻った段階での修正・次問移動を妨げない。今回の最終段階の進級テストを完了したときだけ修了への導線を表示する。
- 提出RPCのラッパーも、冪等キーを確認する前に学習者の進捗行をロックする。競合する同一提出による進級カウントの二重更新を防ぐ。

### トークン効率と将来のEmbedding

- Claudeへ渡すのは、今回の段階設計、狙う技能コード、題材コード、必要な論証・資料条件、避ける直近指紋だけとする。過去答案、全問題文、全特徴ベクトルは渡さない。
- 初期の題材は管理済み分類なので、カテゴリコードと利用回数で十分に多様性を管理できる。自由入力の新規テーマが増え、既存分類へ安定して割り当てられなくなった時だけ、短い`topic_summary`を1本Embedding化する。
- Embeddingを追加しても、段階別技能、論証方法、資料構造などの明示的特徴を置き換えない。説明可能な特徴署名を主、Embeddingを未知テーマの補助とする。

### AI利用量とコスト制御

- 問題生成は承認済み問題バンクを最優先し、狙う技能に合う未出題問題がない場合だけAIを呼ぶ。AI生成問題は検証後に共有問題バンクへ保存し、同じ生成費用を複数学習者で再利用する。
- 添削は答案ごとに必要なため、問題生成より多くの予算を割り当てる。過去答案や全履歴は添削入力へ含めず、今回の問題、答案、対象技能、必要なルーブリックだけを送る。
- 現在の数値（問題生成1回あたり入力1,800・出力700トークン、学習者1日3回、添削1回あたり入力6,000・出力1,800トークン、学習者1日20回）は、開発中の暴走を防ぐためだけの**暫定ガード値**である。問題と添削の品質へ直結するため、本番仕様・料金プランとして確定してはならない。
- 実請求の集計には推定値ではなく、プロバイダー応答の入力・出力・キャッシュ作成・キャッシュ読込トークンを使う。`ai_usage_events`へ処理種別、モデル、状態、各トークン数、料金表版、任意の概算費用を保存する。
- 料金単価とモデル名をアプリへ固定しない。`ai_budget_policies`の上限とサーバー側環境設定で変更できるようにし、ブラウザへAPIキーや内部原価を渡さない。
- 予算超過、生成無効、検証失敗時も学習を止めず、承認済み問題またはローカル問題へフォールバックする。添削の予算超過時は、正式添削を行っていないことを明示して再試行可能な状態を返し、モック結果を正式成績として保存しない。

## 認証・DB接続済みのローカル開発版

- 認証はSupabase Authのメール＋パスワードを使用する。確認メールと再設定メールの戻り先は、Supabase AuthのURL allow-listで限定する。
- Supabase接続済み環境の初回入口は`/login`とし、同じ画面でログインと新規登録を切り替える。未ログインでアプリ本体へアクセスした場合は`/login`へ案内し、ログイン後はホームへ進む。パスワード再設定のリンクだけは`/account`へ戻し、新しいパスワードを設定する。
- `web/.env.local`にProject URLとPublishable keyを置く。前者は接続先、後者はブラウザ用の公開キーであり、Git管理しない。
- 未設定時だけローカル体験版として動かす。Supabase設定済みの未ログイン状態ではローカルデータを表示・保存せず、ログインを求める。既存のローカルデータを無断でクラウドへ移さない。
- 学習者の下書き、提出、添削結果は正式テーブル`drafts`、`submissions`、`feedback_results`へ保存する。試作用の重複テーブルは作らない。
- `learning_progress`に現在段階、最高到達段階、学習フェーズ、フェーズ内合格・受験数、3種類の回数設定、全課程修了日時を保存する。学習者が直接更新できるのは3種類の回数設定だけとし、段階移動は上限を検証するDB関数を経由する。
- `problem_history`に発行済み問題、発行時の学習フェーズ、段階別`feature_signature`、問題指紋、本文ハッシュ、設計・生成版、発行・提出日時を保存する。ブラウザには本人分だけを返し、発行は現在段階を検証するDB関数を経由する。
- 下書きは500msのデバウンスと直列保存で競合を防ぐ。提出前には保留中の下書き保存を完了させる。
- モック提出は`request_id`で冪等化し、提出・添削結果保存・下書き更新または削除・フェーズ判定・進級を`submit_mock` DB関数の1トランザクションで行う。要修正なら問題を未完了のまま下書きを保持し、合格済み問題への再送は二重計上しない。Claude接続時は同じ境界をEdge Functionへ置き換える。
- 問題発行は学習進捗行をロックして直列化し、同じ段階ですでに未提出問題があれば新規発行しない。ローカル保存でも同じ制約を適用する。
- Data APIのテーブル自動公開は無効とし、必要な`authenticated`権限だけをマイグレーションで明示的に付与する。
- `profiles`は認証済み学習者に対して`display_name`列だけを更新許可する。`role`列の更新権限はPostgreSQLの列権限で明示的に剥奪し、RLSだけに依存しない。
- パスワード再設定は`PASSWORD_RECOVERY`イベントを検出し、確認用入力後に`updateUser`で完了させる。
- オンライン提出はSupabaseの`feedback` Edge Functionだけが受け付ける。関数はSupabase Authで利用者を確認し、STEP 1・3・4をClaude Haiku 4.5、STEP 2・5〜14をClaude Sonnet 4.6へ振り分ける。モデルIDはサーバー環境変数で差し替え可能とする。Anthropicの構造化出力とアプリ側検証を併用し、対象技能の過不足や判定矛盾がある結果は成績へ保存しない。
- オンラインでは`request_id`ごとにAI呼び出しを事前予約し、同じIDの二重課金・二重進級を防ぐ。予約、暫定予算判定、Claude呼び出し、検証、正式提出、使用量記録をEdge Functionとサービス専用DB関数の境界に置く。ブラウザから`submit_mock`を実行する権限は廃止する。タイムアウトや提供元エラー時はモック判定へ落とさず、未提出のまま再試行可能なエラーを返す。
- ローカル試作モードは実行時に外部生成AIを呼ばず、問題と添削を決定的に作る。ローカルの結果は正式なオンライン成績へ混ぜない。

ローカルMVPはClaude、Stripeの代替ではない。認証、DB保存、RLSの実接続確認後にClaude添削と課金を接続する。
