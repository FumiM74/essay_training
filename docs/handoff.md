小論文添削システムのサービス化 — 引き継ぎドキュメント

このドキュメントは、個人開発した「小論文添削自動化システム(Google Apps Script版)」を 一般向けの有料サービスにスケールするための議論を、新しいチャットスレッドで進めるための 引き継ぎ資料である。このドキュメント単体を読めば、経緯・現行の仕組み・つまずいた点・ スケール構想のすべてが把握できるように書いてある。

議論がまとまったら、その結論をコード実装(別途)に渡す想定。

## 0. このプロジェクトのゴール

やりたいこと: 大学受験の小論文対策を、AI(Claude)による自動添削で支援する学習サービスを、 個人のサブビジネスとして立ち上げ、マネタイズする。

開発方針: 決済・認証・メール・エディタなど「重い部品」は自作せず、テック企業の 既製サービスをつなぎ込む(オーケストレーションに徹する)。開発者が管理するコード量と エラー要因を最小化する。

現状: Google Apps Script版が完成し、1〜数人での実運用・価値検証フェーズにある。 この検証は現行スレッドで継続する。本ドキュメントを受け取る新スレッドは「サービス化の 設計議論」を担う。

## 1. 教育メソッド(サービスの中核価値)

「文章が書けない原因の多くは思考力不足ではなく、文章の型が身についていないこと」という 前提に立つ。初期段階は思考負荷を下げ、型を反復で自動化することを最優先。型が無意識に 使えるようになってから、読解・意見形成・小論文へと進む。添削品質は渡すプロンプトに依存する ため、この教育設計こそがサービスの資産である。

7段階の学習フロー

志望分野: 情報科学、デザイン(※建築は運用途中で削除した経緯あり。分野は可変設定)

教材の中心テーマ: 人間中心設計、ユニバーサルデザイン、認知心理、情報社会、 AIと人間、都市設計、公共空間、建築と行動、デザイン思考

段階の進め方(重要な運用ルール)

段階を上げるときは、未取り組みの問題ファイルを削除してから段階設定を上げ、次の問題を生成する。

段階ごとに個別指示(学習者ごとのクセへの対応など)を追加できる仕組みがある。

## 2. 現行システム(Google Apps Script版)の仕組み

基本設計

「1問1ファイル」でGoogle Docsに問題・全回の解答・全回の添削を積み上げる方式。 学習者はメールで課題を受け取り、Docsに解答を書いてメールに返信するだけ。 フォルダ移動もボタン操作も不要。

フォルダ構成(1つの管理者Googleアカウント内)

共有ディレクトリ/

├─ 00_進行管理          Google Doc(段階管理: 「現在の段階: N」を書き換える)

├─ 01_新規問題          出題中の問題

├─ 02_取り組み済        フォールバック用(通常未使用)

├─ 03_添削済            要修正で差し戻し中

└─ 04_終了              合格・完了

加えて、処理ログ用のGoogleスプレッドシートを1つ使う。

処理の流れ

createNewProblem が問題を生成し、01_新規問題にGoogle Docsを作成、メール通知。

学習者がDocsの「■ 解答(第N回)」の下に解答を書き、通知メールに返信。

watchEmailSubmissions(トリガーで定期実行)が未読の返信を検知し、gradeSubmissionを呼ぶ。

Claudeが添削し、同じDocsに追記。

要修正 → 03_添削済へ移動、同スレッドに「判定:要修正」を返信。

合格 → 04_終了へ移動、次の問題を自動生成、「判定:合格」を返信。

合格→次問題生成→…とループが自走する。最初の1問だけ手動で生成。

メール設計

件名は全メール共通で 【小論文添削】[ID:ファイルID] に固定(件名変更でスレッドが割れるのを防ぐ)。

状況(新規課題/要修正/合格)は本文の冒頭に明記。

1問1スレッドで完結。スレッドIDをスクリプトプロパティに保存して同一スレッドを維持。

テストモードと本番モードで挙動が同一になるよう統一済み。

ファイル構成(11本の .gs + README)

Config: 設定値(APIキー、各フォルダID、メールアドレス、TEST_MODE、FIELDS=志望分野)。

RubricData: 段階別ルーブリック(STAGE_RUBRIC)、進行管理Docの読み取り。

DocStructure: Docの見出し構造の生成、最新の解答の抽出。

ClaudeClient: Claude API呼び出し。学習メソッド説明をプロンプトキャッシュ化(コスト約10%)。

LogSheet: 処理ログ、重複処理防止、直近20件の出題テーマ記録(テーマ多様化用)。

Notifier: メール送信。スレッドIDを保存し同一スレッドを維持。

MailWatch: メール返信監視。未読のみ検索。空提出には案内メールを返す。深夜1:00〜6:00は停止。

ProblemCreation: 問題生成。分野ローテーション＋直近20テーマ回避＋ランダムシードで多様化。

SubmissionGrading: 添削本体、ファイル移動、合格時の次問題生成。

CompletionChecker: 手動フォールバック(先生が手動で04_終了に入れた場合の次問題生成)。

Triggers: トリガー設定(1分ごと)。

補助: TeacherReview(04_終了の全ファイルを段階ごとにまとめ、先生用の全体確認Docsを生成)。

多様性・コスト対策

問題の繰り返し防止: 処理ログに直近20件の出題テーマを記録し、それらを避けるよう指示。 さらに志望分野のローテーションと時刻ベースのランダムシードを併用。全過去を渡すと トークンが増え続けるため、直近20件固定にしている。

トークン節約: 学習メソッドの固定説明部分をプロンプトキャッシュ化し、通常の約10%のコストで参照。

## 3. Google Apps Script版でぶつかった制約(スケール時に必ず回避すべき教訓)

これらは「1つのGoogleアカウントに全員を間借りさせる」構成の限界であり、実運用で実際に発生した。 サービス化では、これらが構造的に起きないアーキテクチャを選ぶことが重要。

Gmailの1日あたり呼び出し回数上限(約20,000回): 1分ごとに全スレッドを検索・走査すると 上限に達し「Service invoked too many times for one day: gmail」で丸1日停止した。 → 未読のみ検索＋処理後に既読化、深夜停止(1:00〜6:00)で対処した。

Apps Scriptの実行時間上限(個人は1日90分): トリガーの積み重ねで到達しうる。

トリガーの制約: 時間主導トリガーの最短は1分。指定可能な間隔は1,5,10,15,30分のみ(2分は不可)。 1プロジェクトのトリガー数は最大20個。→ 学習者が増えると破綻する。

Google Driveの検索インデックス反映遅延: 合格直後にファイル移動すると、移動前の状態が 見えて誤判定することがあった。→ 合格時はガードをスキップして確実に次問題生成。

Gmailのスレッド/アーカイブ/ミュートの挙動が不安定: 件名変更でスレッドが割れる、 自動アーカイブで受信トレイに出ない等。→ 件名固定、状況は本文に、で回避。

Google DocsのチェックボックスAPIの制約: チェック状態を取得できず、提出トリガーに使えない (採用を断念しメール返信方式にした)。

standaloneスクリプトのUI制約: 動的生成した他ファイルにメニューを追加できない (Docs内ボタン方式を断念した経緯)。

提出手段の変遷: Docsフォルダ手動移動 → チェックボックス → Webアプリのボタン → 最終的に「メール返信で提出」に落ち着いた。学習者の手数を最小化しつつ確実に動く方式を選んだ結果。

## 4. サービス化の設計(議論のたたき台)

採用モデル: 薄いバックエンド ＋ 既製サービスのつなぎ込み

裏側は1つの共通バックエンド。ユーザーには「自分専用の学習空間」に見せる (マルチテナント: データベースのユーザーIDでデータを分離)。今のGoogle方式の 「フォルダで分ける」発想を「ユーザーIDで分ける」に置き換えるだけで概念は同じ。

機能ごとの採用サービス候補(日本国内向け)

実質使うのは Stripe / Supabase / Resend / Claude API の4つ。

全体像(想定)

[STUDIO のLP] → 申し込み

[Stripe] 課金・サブスク管理 → 支払い完了

[Supabase] ログイン・ユーザーごとのデータ保存 → 解答を保存

[Supabase Edge Function] ← Apps Scriptロジックの引っ越し先 → 添削依頼

[Claude API] 添削 → 結果保存＋通知

[Resend] メール通知

この構成が現行の制約を解消する理由

トリガー実行時間・回数の上限 → サーバーレスなので実質問題にならない。

Driveのインデックス遅延 → DBは即時反映で発生しない。

Gmailのスレッド/アーカイブ問題 → 専用メールサービスで発生しない。

UIの制約(チェックボックス等) → 自前画面で自由に作れる。

マルチテナント → DBのユーザーID＋行レベルセキュリティで安全に分離。

## 5. マネタイズ設計(議論のたたき台)

課金方式: 月額サブスクリプション(Stripe Billing)。年額割引も検討可。

コスト構造: 主コストはClaude APIの従量課金。1学習者あたり月数十〜数百円程度。 月額数百〜千円台のサブスクなら利益が出る。

無料導線: 「最初のN問は無料」等の体験導線で獲得。

決済手段: コンビニ払い・銀行振込にも対応でき、カードを持たない高校生でも保護者が 払いやすい(教育サービスと相性が良い)。

## 6. 推奨する実装ステップ(リスクの低い順)

各ステップが独立して動作確認でき、問題の切り分けがしやすい。

Supabaseで「ログイン→解答入力→保存」だけ作る(課金なし・自分だけ・メールなし)。

Edge FunctionでClaude添削をつなぐ(保存された解答が添削されて画面に返る)。

Resendでメール通知を足す。

Stripeで課金を足す(数人の有料テスターで検証)。

STUDIOでLPを作り一般公開。

並行して、現行のGoogle Apps Script版で教育メソッドとしての価値検証を継続する。

## 9. このタスクで確定したサービス設計（次スレッドへの引き継ぎ）

以下は、この引き継ぎ文書を読んだ後に進めるべき、サービス化設計の確定事項である。Google Apps Script版のメール監視型の運用を、スマホ対応Webアプリ（PWA）でのリアルタイム学習に置き換える。

9.1 学習体験と運用方針

学習者はメールやGoogle Docsを使わず、Web画面だけで問題閲覧、解答、送信、添削受信、再提出、次課題への移行を行う。スマホ対応のPWAとして提供する。

提出と同時に添削し、画面へ返却する。Gmailの定期監視、未読検索、メール返信を提出トリガーにする実装は外す。

解答の下書きは自動保存する。提出・添削・再提出の履歴は学習者ごと、課題ごとに時系列で保持する。

メールは学習の中核にしない。障害連絡、領収・決済、必要な案内だけを送る任意の補助機能とする。

9.2 初期採用アーキテクチャ

Cloudflare Pages：PWAの画面（静的配信）。

Cloudflare Workers：添削API、認証済み要求の受付、Claude/OpenAI API呼び出し、決済Webhook、入力・AI出力の検証を担う。APIキーをブラウザに渡さない。

Supabase：認証、PostgreSQL、行レベルセキュリティ（RLS）、リアルタイム反映。学習者ごとのデータを user_id で分離する。

Claude APIを初期の添削モデル候補とする。OpenAI APIへ差し替えられるよう、Worker内の添削エージェントをモデル固有部分から分離する。

Cloudflare Queues：初期は必須ではない。添削待ち・再試行・負荷平準化が必要になった段階でWorkerの後段に追加する。

Cloudflare R2：初期の本文履歴には不要。PDF、画像、教材添付、出力ファイルを扱う段階で追加する。

Resend：決済・アカウント・障害などのトランザクションメールに限定して後から追加する。

STUDIO/FramerはLP制作の選択肢ではあるが、学習アプリの必須構成要素ではない。初期はPagesでLPとアプリをまとめてもよい。

9.3 データ保存と個人情報

有料の複数学習者サービスでは、履歴をファイル辞書だけで管理しない。並行アクセス、履歴の版管理、本人だけへのアクセス制御、決済状態との連動のため、提出・添削・進捗はDBで管理する。

アプリが保持する個人情報は最小化する。氏名、住所、電話番号、カード情報をアプリDBへ集めない。決済情報は決済事業者に任せる。

ただし、小論文本文と学習履歴も個人情報として扱う。認証、RLS、暗号化された通信、削除要求への対応、保持期間を設計対象にする。

基本テーブル案：profiles（最小プロフィール）、tasks、submissions、feedback_results、learning_progress、entitlements（利用権）、payment_events、rubric_versions、instruction_versions。

9.4 決済方針（日本の高校生を想定）

スマホ対応Webアプリ／PWAで開始する。ネイティブアプリのストア課金は初期に採用しない。

保護者・教師向け：Stripeのクレジットカードによるサブスクリプション。

学生向け：Stripeで提供可能なPayPayとコンビニ払いを併用し、30日・90日などの買い切り利用権として提供する。コンビニ払いを継続課金の主軸にしない。

キャリア決済は後から実装する。初期DBには payment_provider と source_type 等の拡張可能な区分だけ用意する。

9.5 添削エージェントの基本設計

Claudeはサービス運営者がAPI契約し、Workerが利用する。利用者にClaudeアカウントやAPIキーを使わせない。

専用エージェントをローカル常駐させたり、利用者ごとに無期限の会話記憶を持たせたりはしない。各提出で必要な固定指示、現在の段階設定、課題、今回の本文、短い前回フィードバックだけをWorkerから渡す。

固定指示は毎回論理的には参照されるが、静的部分を先頭に固定してプロンプトキャッシュを利用し、トークン費用を抑える。全履歴や全カリキュラムを毎回渡さない。

学習者が入力する課題文・解答・指示風の文章は、添削対象のデータであり、AIへの命令として扱わない。

AIは自由文ではなくJSONのみを返す。WorkerがJSON Schemaで検証し、失敗時だけ限定回数の再生成を行う。検証できない出力は保存・表示しない。

9.6 13段階の学習ロードマップ

従来の7段階を、習得単位ごとに次の13段階へ細分化した。標準の進級条件は「3問連続合格」だが、管理者が個別に変更できる。

0 初回診断／1 一文完成／2 一文を明確にする／3 主張を書く／4 理由をつなぐ／5 理由を深める／6 具体例を添える

7 四文段落／8 文章構造を読む／9 要約する／10 根拠ある意見／11 別視点を扱う／12 ミニ小論文／13 本番小論文

9.7 全段階に先行する日本語文成立チェック

段階別評価とは別に、毎回最初に日本語文として成立しているかを確認する。問題がなければ評価・コメントを表示しない。問題がある場合だけ、段階評価の前に添削する。

status は clean / minor_issue / revision_required。revision_required のときは、その提出を段階合格にしない。

指摘は最大3件に絞る。分類は主語述語、修飾、助詞、接続、並列、省略、指示語、時制、論理関係、誤記など。

「不自然」で終えない。問題の箇所、文法・意味上の関係がどこで壊れるか、読者がどう読み違え得るか、直し方、短い修正例を丁寧に示す。

サンプル文だけに依存しない。ねじれ文、主語の欠落、係り受けの曖昧さ、接続・因果関係の誤りなど、様々な不成立文に一般化して対応する。

9.8 本番小論文（段階13）の終了ルール

管理者が合否を付けない。日本語文成立チェックが clean、設問に適合、主張・根拠・具体例・結論の論理構成が一貫、小論文として一定の到達水準に達していることを合格条件とする。

合格は「改善点がない」ことではない。合格後も、より明確にできる点・根拠を深められる点を具体的なコメントとして残す。再提出時は前回の改善点にどう対応したかも添削する。

終了を決めるのは学習者。AIや管理者が改善余地を理由に終わらせない。

ただし、現論文の質が十分で次課題へ進む方が学習上有効な場合は、改善コメントとは別に、理由を添えて「この論文を終了して次の課題へ進む」選択肢を穏やかに提案する。強制しない。

9.9 添削APIの入出力契約（実装時の基準）

入力：request_id（冪等性）、stage_id、task_id、submission_text、revision_no。課題本文・学習者ID・前回フィードバック要約・ルーブリック版・固定指示版は、可能な限りWorkerがDB/JWTから取得する。

出力：schema_version、日本語チェックのstatusとissues[]、段階評価、decision（pass/revise）、優先フィードバック最大3件、再提出時の前回指摘への対応評価、本番用 completion_guidance（continue/may_finish/null）。

clean の日本語チェックは画面にコメントを出さない。revision_required は必ず revise。may_finish は段階13で十分な到達水準のときのみ返す。

提出結果には、使用した rubric_version と instruction_version を固定保存し、後から評価基準が更新されても過去の結果を再現できるようにする。

9.10 次のタスクで着手する順序

SupabaseのデータモデルとRLS方針を、上記テーブル案・API契約に沿って確定する。

Cloudflare Workerの添削エンドポイント（認証、入力検証、AI呼び出し、JSON Schema検証、保存）を実装する。

PWAの最小画面：ログイン、課題、解答エディタ（自動保存）、提出、添削結果、履歴、次の選択を実装する。

課金は学習機能が動いてから追加する。Stripeカードの定期利用権、PayPay・コンビニの期限付き利用権、Webhookによるentitlements更新を実装する。

AIの固定共通指示と段階別ルーブリックは、人が管理しやすいExcelを正本とし、実装用のJSONへ変換してバージョン管理する。

9.11 同梱の設計資料

同じ作業フォルダに「小論文添削サービス_カリキュラム設計.xlsx」がある場合は、こちらも読むこと。13段階のルーブリック、日本語文成立チェックの評価設計、AI指示設計、添削APIの入出力契約を表形式で収録している。Excelは人が編集する正本、アプリで読むJSONはそこから生成する前提である。
